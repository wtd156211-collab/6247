# 二进制补丁生成与应用（从 0 实现）

起始环境只有说明与素材：`samples/` 是新旧文件对、坏补丁与逐行期望；引擎、报告与测试都从零写。
Python 3.13、标准库，入口固定 `python -m diffpack <子命令>`。

## 1. 范围

做的：补丁引擎（库 + 命令行）——`diff` 生成、`apply` 应用、`report` 出静态 HTML 报告；`unittest` 测试只读
`samples/`（`python -m unittest discover` 跑通）。

不做：目录扫描与传输、压缩、加密与签名、链式补丁、交互式页面、`samples/` 之外的输入、坏补丁之外的非法输入
提示、第三方库/CDN/构建。

## 2. 口径与公式

### 2.1 段模型

新文件 = 段表里各段按序拼出的字节串。段只有两种：`C` 从旧文件复制，`I` 是字面量（字节写在补丁里）。
第 i 段的起点 `new-start_i` = 前 i 段长度之和，段表因此把新文件切成首尾相接的块，`Σ len = new-size`；
`C` 段来源区间要落在旧文件内。

### 2.2 补丁大小与上界

补丁大小 = 补丁文件字节数。格式自带的上界 `≤ 256 + 80×K + L`（K 段数、L 字面量字节数）。样例上界写在
`samples/expected/<case>.txt` 的 `patch-max`，生成端不得超；上界留余量，不追极限压缩。

### 2.3 校验

- 文件级：`old-sha256`、`new-sha256` 是整份文件的 sha256（64 位小写十六进制）；`old-sha256` 同时是基线版本标识
  （差一字节即另一个），应用端拿它做基线匹配。
- 段级：每段一个 `crc32`（`zlib.crc32(该段产出的字节) & 0xffffffff`，8 位小写十六进制）：`C` 段算旧文件
  `[old-start, old-start+len)`，`I` 段算字面量区里对应的字节。

### 2.4 条带口径

块长 `L = ceil(max(旧大小, 新大小) / 512)`，第 j 块覆盖 `[j×L, min((j+1)×L, 大小))`。老带：与任一 `C` 段来源区间
有交 → 「原样复制」，否则「被删掉」；新带：与任一 `I` 段区间有交 → 「新增」，否则「原样复制」。颜色只由本次
生成的段表决定。

## 3. 数据结构与处理顺序

### 3.1 补丁布局

头部 6 行 ASCII + 段表 K 行 ASCII + 字面量区（原始字节，按 `I` 段先后首尾相接；没有 `I` 段时为空）：

```
DIFFPACK 1
old-size <十进制>
old-sha256 <64 位小写十六进制>
new-size <十进制>
new-sha256 <64 位小写十六进制>
blocks <K>
C <new-start> <old-start> <len> <crc32>
I <new-start> <len> <crc32>
```

十进制无符号、无前导 0（0 写 `0`），单个半角空格分隔，每行 LF 结尾；首段 `new-start` 为 0，后一段等于前一段
之尾，`len ≥ 1`，`old-start + len ≤ old-size`。

### 3.2 生成端规范形

同一对文件只允许一种写法（否则「两遍相同」没法对标）：相邻同类段必须合并——两个 `C` 段在旧文件里也连续
时必须并成一段，字面量不许拆成相邻两段。匹配策略自由，但不许有与「旧 × 新」成正比的结构。

### 3.3 应用端处理顺序

① 读满头部与段表 K 行，按声明核对字面量区长度；读到一半没字节了 → `TRUNCATED`。② 核对 `old-size`、
`old-sha256` 与实参旧文件 → `BASELINE-MISMATCH`。③ 逐段重算 `crc32`、再重算 `new-sha256` →
`CHECKSUM-MISMATCH`。三道闸门都过才写输出；拒绝时不写字节，补丁尾部多出字节也算非法。

## 4. 输入输出与文件格式

### 4.1 命令行与退出码

```
python -m diffpack diff   <旧文件> <新文件> <补丁文件>
python -m diffpack apply  <旧文件> <补丁文件> <输出文件>
python -m diffpack report <旧文件> <新文件> <报告文件> --patch-max <字节>
```

都在仓库根目录执行，只写参数指定的文件。退出码：0 成功、2 参数错、3 拒绝、1 其它失败。

### 4.2 拒绝分类

`apply` 拒绝时退出码 3，stderr 一行以类别开头、后面带补丁路径：`BASELINE-MISMATCH`、`CHECKSUM-MISMATCH`、
`TRUNCATED`。三类之外的非法补丁也必须拒绝、不写文件，类别不查。

### 4.3 diff 的输出

`diff` 往 stdout 写一行 JSON（键序固定、秒数三位小数）：
`{"patch_bytes": 413, "blocks": 7, "copy_bytes": 65488, "insert_bytes": 48, "gen_sec": 0.004}`。

### 4.4 展示这一侧（报告）

`report` 内部先跑一遍生成，把补丁画成静态 HTML 写进参数给的路径（习惯叫 `patch-map.html`）：单文件、无外部
资源、无脚本，双击能开。必须体现：

1. 顶部：两份文件名（不写绝对路径）、字节数、`old-sha256` / `new-sha256`。
2. 两条横带（老在上、新在下）：块长、块数与两类颜色占比（一位小数），图例「原样复制 / 被删掉」「原样复制 /
   新增」。
3. 补丁大小与 `--patch-max` 上界，及「达标 / 超标」。
4. 生成耗时（秒，三位小数）。
5. 校验结果三行：基线 sha256、逐段 crc32、应用结果与 `new-sha256`，各写「通过 / 不通过」。

## 5. 性能与验收口径

### 5.1 规模与预算

八百兆的热更新包放不进仓库：`samples/pairs/bulk`（旧 4 MiB / 新 3.5 MiB）是同一路径的缩样，现场包自备（见 §7）；
两份输入不许整个读进内存。

- 生成端：`tracemalloc` 包住一次 `diff`，额外峰值 ≤ **48 MiB**，且不随输入变大（几百兆的包同样 48 MiB）。
- 时间：`bulk` 上 `diff` ≤ **60 秒**、`apply` ≤ **30 秒**（单进程单机、含读写）；几百兆的包几分钟内出补丁。

### 5.2 验收（逐条）

1. 环境与预算：Python 3.13、标准库、无构建，入口 `python -m diffpack`；5.1 的内存与时间。
2. 正确性：每对样例 `apply(旧, diff(旧, 新))` 与 `new` 逐字节相同，sha256 = `result-sha256`。
3. 大小：每对样例的补丁字节数 ≤ 该样例 `patch-max`。
4. 拒绝：三个坏补丁按 `expected/rejections.txt` 给出类别，且不写输出文件。
5. 复现：同一对跑两遍 `diff`，补丁 sha256 一致；跑两遍 `report`，除耗时数字外逐字节相同（不写时刻、随机数、
   绝对路径）。
6. 报告：按 4.4 生成、双击能开、五项齐全；补丁大小与段数 = 单独 `diff` 写出的补丁。
7. 测试：`python -m unittest discover` 跑通，用例只读 `samples/`。

## 6. 样例说明

`pairs/<case>/{old,new}` ↔ `expected/<case>.txt` 一一对应，期望文件固定三行：`result-size`、`result-sha256`
（应用结果即新文件）、`patch-max`。

| 样例 | 旧 / 新字节 | 覆盖点 |
| --- | --- | --- |
| `inplace` | 65536 / 65536 | 三处 16 字节原地改写 |
| `insert` | 65536 / 69632 | 中间插入 4 KiB |
| `delete` | 65536 / 57344 | 摘掉两段各 4 KiB |
| `tiny` | 32768 / 32768 | 只有三个字节变了，分散在三处 |
| `shift` | 262144 / 263168 | 大段位移：尾巴 100 KiB 挪到头部，再插 1 KiB |
| `unrelated` | 32768 / 32768 | 几乎完全不同：只共享 256 字节头 + 128 字节尾 |
| `bulk` | 4194304 / 3670016 | 删 1 MiB、插 512 KiB、尾段位移、八处 32 字节改写 |

`bad-patches/` 三个坏补丁与 `expected/rejections.txt` 一一对应，每行三段（`<补丁> <旧文件> <类别>`，路径相对
`samples/`，按补丁名升序）：`bad-baseline.patch` 是 `tiny` 的补丁配 `pairs/unrelated/old`（大小同、
内容不同，考基线哈希）；`bad-checksum.patch` 把 `inplace` 补丁字面量翻掉一位；`bad-truncated.patch` 掐掉
`inplace` 补丁最后 24 字节、停在字面量区里。

逐条核对：`python -m diffpack diff samples/pairs/inplace/old samples/pairs/inplace/new var/inplace.patch`，
stdout 的 `patch_bytes` ≤ 该样例的 `patch-max`；`apply` 出的文件 sha256 = `result-sha256`；`report ... --patch-max
2048` 的页面双击能开。`samples/notes.md` 是现场记录，合计约 8.5 MiB。

## 8. 匹配引擎口径（本实现，供跨语言复现）

§3.2 只约束规范形；要得到与本实现逐字节相同的补丁，匹配策略按下面来。全程流式：两份输入只做只读
映射，索引是定长开地址哈希表，内存不随输入变大。

1. 窗口 `B` = 不小于 `ceil(old-size / 2^20)` 的最小 2 的幂，且至少 64。旧文件越大的只是最小可匹配
   长度变大，字面量粒度不受影响（靠下面的两侧扩展）。
2. 旧文件索引：只取完整对齐块 `[i×B, (i+1)×B)`（`i < floor(old-size / B)`），键 =
   `zlib.crc32(块)`。槽数 = 不小于 `2×块数` 的最小 2 的幂（至少 `2^12`），槽值 =
   `(crc << 21) | (块号 + 1)`，`0` 表示空槽，线性探测；同一 crc 只保留最早块号。
3. 扫描新文件，游标 `p` 从 0 起：查窗口 `[p, p+B)` 的 crc32；命中且对应旧块逐字节相等，则以
   `(旧块起点, p)` 为锚向两侧扩展——向后不越过上一段之尾与旧文件起点，向前不越出两份文件——
   发段后 `p` 跳到匹配之尾；否则 `p += 1`。逐字节相等的核对优先于 crc，crc 撞车不等于匹配。
4. 发段：匹配前若有未覆盖字节先发 `I` 段，再发 `C` 段；扫完（含 `p + B > new-size` 的尾巴）残余
   字节发 `I` 段。随后按 §3.2 合并：相邻 `C` 段在旧文件里也连续时并成一段。
5. 段 crc32、文件 sha256、补丁字节布局全部按 §2.3、§3.1；同一对文件跑两遍，索引构造、探测顺序、
   扩展结果都是确定的，补丁逐字节相同。
